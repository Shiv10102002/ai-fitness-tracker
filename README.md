# 🏋️ AI Fitness Tracker — Microservices

[![CI](https://github.com/Shiv10102002/ai-fitness-tracker/actions/workflows/ci.yml/badge.svg)](https://github.com/Shiv10102002/ai-fitness-tracker/actions/workflows/ci.yml)

A full-stack fitness tracking application built with a **microservices architecture**. Users can log workouts and instantly receive **AI-powered analysis and recommendations** generated by Google Gemini. Authentication is handled by **Keycloak** using the OAuth2 PKCE flow, and activity events are streamed asynchronously via **Apache Kafka**.

              ┌────────────▼──┐   ┌───▼────────────┐

              │  port: 8081   │   │  port: 8082     │
              │  PostgreSQL   │   │  MongoDB        │

                                          │ Kafka Event

  Eureka Server    → localhost:8761  (Service Discovery)

## Features

### 🔐 Authentication & User Management
- **OAuth2 PKCE login** via Keycloak — no passwords stored in the app
- **Automatic user sync**: on first login, the gateway reads the JWT and silently registers the user in the User Service
- Users can log in and log out from the React frontend

### 🏃 Activity Tracking
Log fitness activities with the following details:
- **Activity types**: `RUNNING`, `WALKING`, `CYCLING`, `SWIMMING`, `WEIGHT_TRAINING`, `YOGA`, `HIIT`, `CARDIO`, `STRETCHING`, `OTHER`
- Duration (minutes)
- Calories burned
- Start time and additional custom metrics

### 🤖 AI-Powered Recommendations (Google Gemini)
After every logged activity, an event is published to Kafka. The AI Service consumes it and calls the **Google Gemini API** to generate a structured recommendation containing:
- **Overall analysis** — performance summary
- **Pace analysis** — effort and speed feedback
- **Heart rate analysis** — intensity zone evaluation
- **Calories analysis** — energy expenditure review
- **Improvement areas** — targeted advice per metric
- **Next workout suggestions** — recommended follow-up exercises
- **Safety guidelines** — injury prevention tips

If the AI call fails for any reason, a sensible **fallback recommendation** is saved automatically so no activity is ever left without a response.

### 🛡️ Reliability
- **Idempotent consumer**: a redelivered Kafka event never creates a duplicate recommendation (unique index + pre-check)
- **Dead-letter topic**: malformed or repeatedly failing events are retried, then moved to `activity-events.DLT` so the partition keeps flowing
- **Consistent errors**: all services return RFC 9457 `application/problem+json` with the correct status (400/404/503/500)

### 📊 Activity History & Detail View
- View a full list of all past activities
- Click any activity to see its details alongside the full AI recommendation

## API Reference

All requests go through the **Gateway** at `http://localhost:8080`. Every endpoint requires a valid Keycloak JWT in the `Authorization: Bearer <token>` header.

> **Identity:** the gateway sets `X-User-ID` from the `sub` claim of the *verified* JWT and discards any value sent by the client, so every endpoint only ever returns the caller's own data. See [`specs/001-identity-from-jwt.md`](specs/001-identity-from-jwt.md).

### User Service — `/api/users`

| Method | Endpoint | Auth | Description |
|---|---|---|---|
| `GET` | `/api/users/me` | ✅ Required | Get the caller's profile |
| `POST` | `/api/users/register` | 🔒 Internal only | Called by the gateway on first login (blocked for clients) |
| `GET` | `/api/users/{keyCloakId}/validate` | 🔒 Internal only | Used by gateway / activity-service (blocked for clients) |

No passwords are stored by the application; Keycloak is the only credential store.

---

### Activity Service — `/api/activities`

| Method | Endpoint | Auth | Description |
|---|---|---|---|
| `POST` | `/api/activities` | ✅ Required | Log a new activity |
| `GET` | `/api/activities` | ✅ Required | Get all activities for the logged-in user |

**Log activity request body:**
```json
{
  "type": "RUNNING",
  "duration": 30,
  "caloriesBurned": 300,
  "startTime": "2024-01-15T07:00:00",
  "additionalMetrics": {
    "distanceKm": 5.2,
    "avgHeartRate": 145
  }
}
```

> The `X-User-ID` header is injected automatically by the Gateway from the JWT — you do not need to set it manually.

---

### AI Service — `/api/recommendation`

| Method | Endpoint | Auth | Description |
|---|---|---|---|
| `GET` | `/api/recommendation/user` | ✅ Required | Get all of the caller's recommendations |
| `GET` | `/api/recommendation/activity/{activityId}` | ✅ Required | Get the caller's recommendation for an activity (404 if it belongs to someone else) |

**Recommendation response:**
```json
{
  "id": "...",
  "activityId": "...",
  "userId": "...",
  "activityType": "RUNNING",
  "recommendation": "Overall: Great session...\n\nPace: ...\n\nHeart Rate: ...\n\nCalories Burned: ...",
  "improvements": [
    "Pace: Aim to increase your average pace by 10%"
  ],
  "suggestions": [
    "Interval Training: Alternate between fast and slow running for 20 minutes"
  ],
  "safety": [
    "Always warm up before exercise",
    "Stay hydrated throughout your workout"
  ],
  "createdAt": "2024-01-15T07:35:00"
}
```

## Getting Started

### 1. Clone the Repository

```bash
git clone https://github.com/Shiv10102002/ai-fitness-tracker.git
cd ai-fitness-tracker
```

### 2. Start Infrastructure (one command)

```bash
docker compose up -d
```

This starts PostgreSQL, MongoDB, Kafka (KRaft) and **Keycloak with the
`fitness-app` realm pre-imported** (PKCE client `oauth2-pkce-client` and a demo user
**`demo` / `demo123`**). See [`docker-compose.yml`](docker-compose.yml) and
[`infra/keycloak/fitness-app-realm.json`](infra/keycloak/fitness-app-realm.json).

### 3. Configure Secrets

Secrets are **never** stored in the repo. Config files contain `${ENV_VAR}` placeholders
that each service resolves from its environment:

```bash
cp .env.example .env          # .env is git-ignored; fill in your values
set -a && source .env && set +a
```

| Variable | Used by | Default |
|---|---|---|
| `GEMINI_API_KEY` | ai-service | — (get one from [Google AI Studio](https://aistudio.google.com/apikey)) |
| `POSTGRES_PASSWORD` | user-service, docker-compose | `postgres` |

### 4. Start Backend Services (in order)

Open a terminal per service (with the variables above exported):

```bash
cd eureka          && ./mvnw spring-boot:run   # 1. Service discovery
cd configServer    && ./mvnw spring-boot:run   # 2. Config server
cd userservice     && ./mvnw spring-boot:run   # 3.
cd activityservice && ./mvnw spring-boot:run   # 4.
cd aiservice       && ./mvnw spring-boot:run   # 5.
cd gateway         && ./mvnw spring-boot:run   # 6. Start last
```

Verify all services are registered at: `http://localhost:8761`

> Upgrading from an older checkout? user-service no longer stores passwords. Run
> `ALTER TABLE users DROP COLUMN IF EXISTS password;` once, or recreate the database
> (`docker compose down -v`).

### 5. Start the Frontend

```bash
cd fitness-frontend
npm install
npm run dev
```

Open `http://localhost:5173` in your browser.

### 6. Use the App

1. Click **LOGIN** — you'll be redirected to Keycloak
2. Log in as **`demo` / `demo123`** (or register a new account on the Keycloak page)
3. You're redirected back to the app and auto-registered in the User Service
4. **Log an activity** using the form (type, duration, calories)
5. The activity is saved and a Kafka event triggers AI analysis in the background
6. Click any activity in the list to view its **AI recommendation**

## Environment Configuration

All backend configuration is managed centrally by the **Config Server**. Each service fetches its config on startup from:

```
configServer/src/main/resources/config/<service-name>.properties
```

| Config File | Service | Key Settings |
|---|---|---|
| `ai-service.properties` | AI Service | Gemini API URL & key, Kafka consumer config, MongoDB URI |
| `activity-service.properties` | Activity Service | MongoDB URI, Kafka producer config |
| `user-service.properties` | User Service | PostgreSQL URL, username, password |

Individual services only set `spring.application.name` and the config server URL in their own `application.properties`.

## Testing

Every service has two layers of tests:

| Layer | Naming | Runs with | Needs Docker | What it covers |
|---|---|---|---|---|
| Unit & web-slice | `*Test` | `./mvnw test` | No | Business logic (Mockito), controllers & error mapping (`@WebMvcTest`), gateway security & identity filter, HTTP clients (stubbed `ExchangeFunction`) |
| Integration | `*IT` | `./mvnw verify` | Yes | Real PostgreSQL / MongoDB / Kafka via **Testcontainers**: idempotent registration, activity → Kafka event, Kafka → recommendation pipeline, duplicate delivery, dead-letter routing |

```bash
cd activityservice
./mvnw test     # fast feedback
./mvnw verify   # full suite, as CI runs it
```

Highlights:
- `KeyCloakUserSyncFilterTest`: a spoofed `X-User-ID` is replaced with the JWT subject
- `SecurityConfigTest`: internal endpoints return 403 even for authenticated clients
- `ActivityAIServiceTest`: parses real-shaped Gemini responses, including code-fenced JSON and missing sections
- `RecommendationPipelineIT`: a malformed Kafka message ends up on `activity-events.DLT`

CI ([`.github/workflows/ci.yml`](.github/workflows/ci.yml)) runs `./mvnw verify` for every
service in parallel, plus frontend lint and build, on every push and pull request.
